[R1] Integrator family: implicit — the current INTEGRATOR = Kvaerno5 is correct
     Evidence: the RHS is smooth — products of states, one np.exp() for the Epo
          decay, and nothing else; no sign(), abs(), clip(), floor() or any
          where() on a state-dependent condition. Stiffness is extreme and is
          visible directly in the search box: k_imp_homo is searched over
          [9.77E2, 9.77E6] while k_exp_hetero is searched over [1E-7, 1E-3], so
          a single candidate carries rate constants spanning up to 13 decades,
          and the fast dimer-import and slow nuclear-export processes are
          coupled in the same 8-state system.
     Why: R1 calls for an implicit solver on a smooth RHS with a wide timescale
          ratio. Kvaerno5 appears in the solver table of lib/LLM/api/diffrax.md
          as implicit (stiff) and is marked validated. An explicit method would
          be limited to a step of order 1/k_imp_homo ~ 1E-7 across a 240-unit
          span, which is ~1E9 steps — unreachable at any MAX_STEPS.
     Edit: none — no change needed.

[R7] GRADIENT_OPTIMIZER: adam -> lbfgs, with NUM_ITERS 1000 -> ~50
     Evidence: none of the three conditions that call for adam is present here.
          The RHS is smooth (see R1); the loss in _compute_loss_problem is a
          plain column-scaled RMSE with no NaN masking and no absolute values;
          and the refinement tolerances are tight (STEPSIZE_RTOL = 1E-7,
          STEPSIZE_ATOL = 1E-9), so the gradient is not being computed through a
          loosely-integrated trajectory.
     Why: R7 assigns lbfgs to a smooth, well-normalised loss and reserves adam
          for noisy gradients. L-BFGS is quasi-Newton — it builds a curvature
          model and line-searches, so it converges in tens of iterations rather
          than a thousand, which here would also cut the gradient stage's cost
          by more than an order of magnitude.
     Caveat, stated because it cuts the other way: the source document
          specifies adam for this problem, and the model is known to be sloppy
          (see R9). A sloppy optimum has a near-singular Hessian, which is
          exactly the regime where a curvature model is least reliable. This is
          the one recommendation here that is a genuine judgement call rather
          than a rule application — if the intent is to reproduce the source's
          published number, leave adam alone.
     Edit: <P> GRADIENT_OPTIMIZER = lbfgs </P>   (GRADIENT_OPT/SETTINGS)
           <P> NUM_ITERS = 50 </P>               (GRADIENT_OPT/SETTINGS)

[R9] Identifiability: expect k_imp_homo and k_exp_hetero to be unidentifiable,
     and do not read their fitted values as estimates
     Evidence: this is structural and visible in the RHS, not merely a
          data-scarcity count. k_imp_homo enters only as
          dApA/dt = phos_AA - k_imp_homo*ApA together with
          dnApA/dt = (cyt/nuc)*k_imp_homo*ApA - k_exp_homo*nApA. Once
          k_imp_homo is large the cytoplasmic dimer is in quasi-steady state,
          ApA ~ phos_AA/k_imp_homo, so the nuclear influx (cyt/nuc)*k_imp_homo*ApA
          tends to (cyt/nuc)*phos_AA — with k_imp_homo cancelling out entirely.
          Above that threshold the observables cannot see it at all. The same
          argument applies to k_imp_homo through BpB. Separately, k_exp_hetero
          multiplies nApB, and the three measured observables depend only on
          cytoplasmic species, so k_exp_hetero acts on the fit solely through
          the small material it returns to the cytoplasm.
     Why: both parameters therefore have a direction along which the loss is
          nearly flat, and a global search will settle them arbitrarily — most
          likely against a bound. Expect the sloppiness report to show a wide
          eigenvalue spread. This is not fixed by more iterations or a tighter
          box; only a measurement of a nuclear species would fix it.
     Edit: none — no change needed; read the fitted values of those two
           parameters as "not determined", not as estimates.
